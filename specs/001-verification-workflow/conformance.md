## 2. Requirements without implementation → disposition

- **R1.2 (residual)** — durable engine-step records. Per-step views derive from
  persisted domain rows (design D3). Deferred to Phase 2 with ticket **KAN-66**.
- **R1.16 (residual)** — licence-lapse detection before scheduling is not
  implemented (declared-source enforcement is). Deferred to Phase 2 with ticket
  **KAN-66**.
- **R1.13 (residual)** — atomic cross-process claim: the status check is
  non-atomic and pg-boss singleton keys are unused since case processing moved
  in-process (design D4). In-flight dedupe covers single-process concurrency.
  Deferred to Phase 2 with ticket **KAN-67**.

## 3. Implementation without requirement → removed

Unrequested behaviour is a defect:

1. **Placeholder pg-boss case-processing handler** —
   `services/api/src/workers/worker.ts` contained a `case_processing` queue
   handler that set the case to `processing` and did nothing else ("Placeholder
   for actual processing logic"), while the real pipeline runs in-process from
   the submit route (platform decision, spec §7-D4). Two divergent paths for
   one responsibility. Removed handler + queue registration and the unused
   `case_processing` queue in `services/api/src/workflows/pgboss.ts`.
2. **`withdrawn` fallback on catastrophic processing error** —
   `apps/web/src/lib/server/process.ts` marked cases `withdrawn` when
   `processCase` crashed outside the engine's transactional fallback.
   Withdrawal is a candidate action, not an error state (frozen enum
   semantics); such a write also permanently blocks reprocessing via the
   idempotency gate. Removed; the error is logged and the case remains
   `processing` so a verifier can reprocess.

## 5. Spec updates where design legitimately changed

Recorded in spec.md §7 (D1–D4): input declaration via dependency graph,
four-step consolidation of the original nine-step catalogue, read-time step
projection instead of a durable `case_steps` store, and in-process case
processing instead of a pg-boss queue.
